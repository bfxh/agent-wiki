感知

两条通道，两个频率

外部程序只能读客户端日志，所以整条链路是
「数据包 tellraw → 聊天框 → logs/latest.log → 逐行解析」。
这条链路的延迟完全由数据包的发送频率决定，而一条通道只能有一个频率。

问题是「要什么」是分层的：

要什么变了就得马上知道吗测起来贵吗通道
视线俯仰角是（不然瞄准是开环瞎转）便宜（一条 data get）快
前方有没有墙 / 是不是台阶是（撞上去就走不动了）便宜（8 条 if block）快
准星对着什么方块 / 脚下踩着什么是（挖矿全看这个）便宜快
有几个怪 / 最近的在几格不用贵（遍历实体 + 5 档判定）慢
木头 / 矿石在哪个方向不用很贵（每条 40 条射线）慢
游戏内时间完全不用便宜慢

于是拆成两条：

<TRITF wal=5 b1=2 bd=3 s=1 p=280>                每 2 tick（100ms）
<TRIT  hp=200 food=17 x=.. h=0 d=0 w=6 o=4 t=8000 p=280>   每 20 tick（1 秒）

快通道默认是关的

由 Rust 侧在进入采集/挖矿时发 /function trit_bridge:fast_on 打开，
收手后再延迟 2.5 秒关。

不是为了省那点命令数（合计才 23 条/tick，原版自己每 tick 跑上千条），
而是为了省眼：2 tick 一条等于每秒往聊天框刷 10 行，站着不动也刷。

两帧合并到同一份状态

Rust 侧把两条通道合并到同一份状态上：每条帧只带自己有的字段，
缺的字段保持原值（SensorPatch → Sensor::apply）。

不这么做的话，快帧每 100ms 就会把「有几个怪」清成 0——
AI 会以为世界永远安全。

墙体掩码：一个 8 位掩码塞八个方向

scoreboard players set wal trit_bridge 0
execute at @s rotated ~0 0   if block ^ ^ ^1 #trit_bridge:solid run scoreboard players add wal trit_bridge 1
execute at @s rotated ~45 0  if block ^ ^ ^1 #trit_bridge:solid run scoreboard players add wal trit_bridge 2
...

位序是「相对朝向 yaw 偏移 +i×45°」。

> MC 里 yaw 增加是往右转（0=南、90=西，从南到西是顺时针），
> 所以正右方是位 1、正左方是位 7。
>
> 这个方向感写反过一次，而当时配套的测试也照错的假设写，于是全绿——
> 只在「往右绕墙却撞上左边的墙」时才暴露。
> 改位序前先想清楚 yaw 往哪边加。

延迟是量出来的，不是写死的

「推一下 → 停手等感知 → 再推」里那个「等」，写死一定错：

  • 写 900ms（老的单通道时代），装了快通道也是白装；
  • 写 100ms，只有慢通道时会一路转过头。

所以运行时统计相邻两帧的到达间隔（指数滑动平均，30ms 以下视为同拍重合丢弃），
等 实测间隔 × 1.4 + 30ms。

!gather lag 能直接看到这个数。

实测差多少

通道等多久压 30° 视线要几次用时
慢（1 秒）~1430ms2~3 次~3.6 秒
快（100ms）~170ms2 次~0.7 秒

快通道省下 5 倍时间。 这是整套东西「低延迟」的实际来源。

传感器的代价

慢通道每条要遍历实体、跑 5 档距离判定、40 条射线找木头矿石。
这些是游戏主线程的开销。

所以采集期间 Rust 侧会主动降速——宁可慢，别把游戏卡成 PPT。
MC 侧也有对应开关：

/function trit_bridge:off      # 关掉整个传感器
/function trit_bridge:on       # 打开
/function trit_bridge:fast_on  # 只开快通道
