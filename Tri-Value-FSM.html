三值状态机

为什么不是「做 / 不做」两档

状态机不产出「做/不做」两档，而是每个通道产出 -1 / 0 / +1：

值含义行为
+1明确要执行
-1明确反对反向执行
0不知道弃权，交还给人

关键在于第三档。布尔状态机没有「不知道」——没检测到敌人时，
if (enemy == null) attack(); 里的 attack() 是不执行，但如果写成
if (enemy != null) retreat(); else attack(); 就变成了「没看到就冲」。

三值把「没看到」和「看到没有」分开了。

三条硬规则

（src/fsm.rs）

1. 没人投有效票 → 松手

不会因为「默认值」乱动。所有通道都是 0 时，输出也是 0。

2. 未知票权重 > 已知票权重 → 弃权

这是整个东西的安全底线：

  • 没感知到敌人时它不会瞎打
  • 血量未知时它不会硬冲

也就是说，感知不全 = 动作变小，而不是「按默认值补全」。
这是三值相对于布尔最大的实际收益。

3. 迟滞

  • 从 0 转到 +1 要过 阈值
  • 从 -1 翻到 +1 要过 阈值 + 迟滞

鼠标抖动、日志延迟导致的来回横跳会被吃掉。

一个反直觉的地方

阶段转移表不能直接用 K3 的 and 写。

威胁 AND 血量健康 在 K3 里会得到 Neg（因为 Neg 在合取里吸收），
得出「满血 → 不交战」的错结论。

所以转移写成 3×3 表，见 Machine::next_phase。这不是偷懒，
是 K3 的 AND 在这个语义下真的不对。

从 NPC 那里偷来的战术

整合包里的 hostile_humans、enhancedai、improvedmobs、humancompanions
这几个 mod 的 NPC 打得很像人，但它们的 Goal 类里没有一处是三值的——
全是 if (distanceToSqr < 49.0) 这种硬编码阈值。

我把这些 Goal 反编译，把常量池里的数值一个个挖出来
（(N = x²) 表示原作者写的是 distanceToSqr），然后用三值重写了一遍。
见 src/npc.rs。

移植过来的来源 Goal原始数值三值化之后
交战距离带hostile_humans/MeleeAttackGoal + enhancedai/EARangedBowAttackGoal3 格 / 49.0 = 7² 格远 + 追 / 刚好 0 站住 / 贴脸 - 退半步

最关键的是第一行中间那一档

原版 Goal 只有「靠近」和「开火」两个分支，没有「位置刚好、保持住」这个中间态，
所以 NPC 会一路挤到你脸上互相卡位。

三值化之后这一段是 0，用高权重弃权票表达「位置正好，别推我」——
它天然压掉巡逻和其他前进票，又不会像 - 那样把人推回去。

move 列三段 + / 0 / - 就是这次移植的全部意义。

strategy 列是最上层的战法——它不改行为，只调权重，
所以你能在同一张表里同时看到「底层战术」和「上层战法」各自在做什么。

战法：把《孙子兵法》翻译成加权的票

战法不写 if，而是给某些通道加权。见 src/strategy.rs。

战法加权对象效果
blitz追击权重 ↑敌人远时全力压上
feint虚招权重 ↑反复进出距离带，骗对手先出手
ambush伏击权重 ↑耐心等，等敌人靠近
guard防守权重 ↑血量低时死守不追

因为战法只改权重，它和底层战术不会互相覆盖。同一个表格里能同时看出两层在做什么。
