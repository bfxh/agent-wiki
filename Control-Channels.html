操控方式

以后要接对讲机、语音、第二屏的落地清单

这张表就是「以后要接对讲机、语音、第二屏」的落地清单。
一条操控方式 = 一个 CommandSink 实现，加上这里的一行登记。

为什么要有这张表：能操控什么，取决于有什么通道。
通道不是代码里随便加的几个 if，而是「游戏能收什么、能发什么」的物理事实。
把事实列清楚，别人才知道从哪接手、哪条路走不通。

为什么有些路走不通（省得别人白试）

这几条是查证过的，别再试了：

想法结论原因
直接操控傀儡和狼的移动❌原版 AI 写死在 Goal 里，没有输入注入点。能改的只有 AngryAt / AngerTime 两个 NBT 字段
给村民/僵尸穿上我们的行为❌同上。而且只有 wolf / iron_golem / polar_bear 的 Goal 会读 AngryAt
直接 data modify ... AngryAt set 给刚召出来的宠物设目标❌data modify 只写已经存在的路径。新生实体的 NBT 里没有 AngryAt，命令会被静默拒绝：不报错、不写日志、聊天栏也没提示。必须先 data merge entity @s {AngryAt:[I;0,0,0,0]} 把字段造出来再 modify。同理适用于 Owner
用 SendKeys / 消息队列发键❌Minecraft 走 LWJGL 的原始键盘状态，收不到 WM_KEYDOWN。必须 SendInput
读游戏内存拿坐标⚠️ 不建议可行但每个版本都要重做偏移，还会被杀软当外挂。日志通道够用
让数据包读本地文件❌数据包没有文件系统访问
让数据包「数出附近有几块原木」❌if blocks 只比对两个区域是否相同，不能计数；if block 只测单点。想数就得铺满射线，成本指数上升
外部注入换手持物品⚠️数字键能切快捷栏，但 AI 读不到「第几格是什么」，开环切等于赌博。要么玩家自己换好，要么写 mod
让数据包算出「最近的方块距离」⚠️if block 只测单点，要测距离就得逐格铺射线。所以墙体和准星方块只测 1 格，远处靠慢通道的档位射线
让 #minecraft:solid 一把抓所有固体❌原版没有这个 tag。只能自己拼（16 个 tag + 96 个方块），装了 mod 方块得手工补

怎么实现一条新通道

1. 实现 trait

use trit_agent::squad::{CommandSink, Intent};

pub struct WalkieTalkie {
    port: std::fs::File,
}

impl CommandSink for WalkieTalkie {
    fn kind(&self) -> &'static str {
        "walkie-talkie"
    }

    /// 返回 false = 没发出去（对方没回应、串口断了）。
    /// **不要吞掉失败** —— 上层靠这个返回值决定下一拍要不要重试。
    fn send(&mut self, cmd: &str) -> bool {
        // 长指令压成短码：「/function squad:engage」→ 单字节 0xE1
        let code = match cmd {
            c if c.ends_with(":engage") => 0xE1,
            c if c.ends_with(":recall") => 0xE3,
            _ => return false,
        };
        self.port.write_all(&[code]).is_ok()
    }
}

2. 接到配置上

目前 ControlChannel 是枚举（Off / Dry / Chat），加新通道要改三处：

  1. src/config.rs 的 ControlChannel 加一个变体 + parse / as_str
  2. src/agent.rs 的 drive_squad 加一个 match 分支
  3. DEFAULT_TOML 里的注释

这是已知的扩展摩擦点。
如果你要做第 4、第 5 条通道，值得先把这里改成
「字符串 → 工厂函数」的注册表——这个重构本身就是一个很好的第一个 PR。

3. 登记

在上面的表格里加一行，写清方向（出/入/双向）和依赖。

依赖要写实：需要硬件就说需要硬件，需要装 mod 就说需要装 mod。

4. 加测试

不需要真的对讲机也能测——用一个假串口（Vec<u8> 当缓冲区）验证：

  • 指令被压成正确的短码
  • send 失败时返回 false（而不是静默成功）
  • 上层（Squad）在收到 false 时会重试，不会把状态记成「已发送」

src/squad.rs 的 failed_send_is_retried_not_swallowed 就是这个模式的样板。

对讲机为什么值得做

不是玩梗。它解决一个真问题：移动端操控。

键鼠注入要求你和游戏在同一台机器上。但末日生存整合包经常要挂机——
你去干别的，想隔一会儿问一句「现在什么情况」。
对讲机（或任何低带宽音频通道）
是唯一能在不装 mod、不开端口、不走网络协议栈的前提下传意图的东西。

代价也明确：带宽极低，一条指令只能压成几个字节。
所以它只能承载 squad 的四个意图 + 几个战法开关，承载不了逐帧操控。

> 这也是为什么 CommandSink 设计成意图级而不是帧级——
> 低级通道接进来就能用，不用为它单独降级一套 API。

认领流程

  1. 开一个 issue，用「认领操控方式」模板
  2. 在表里把状态改成 🚧 进行中（@你的名字）
  3. PR 里带上：实现 + 至少 3 个测试 + 表格里的一行
  4. 通道只要能用 dry 通道录下来的同一条指令跑通，就算通过验收
